# Python — remarks

Concrete failure modes seen in LLM-generated code in this repository.
The conventions themselves are in [python.md](python.md).

I have seen the following behaviors generated by the LLM in the past,
please avoid this kind of situations:

## The self-explanatory code for Einstein

```python
def _parse_sum_equality(
    formula: Sequence[dict[str, Any]],
) -> tuple[str, tuple[str, ...]] | None:
```

It is impossible to understand what this function
does without reading the implementation, and even after reading the implementation.

I asked self-explantory code when possible.
But here it is a typical candidate for a
comment explaining what are the typical (input,output) of the function, what is
the purpose of the function. And sometime
(not always, maybe not here) type aliases
can be the solution.
But here the return type is really not clear.

- tuple[TypeA, ...] is good for sequence
- tuple[TypeA, TypeB, TypeC] is often a code smell, and should be replaced by a
  dataclass or at least type alias/annotation
  and a docstring

To know if you should add a docstring,
ask yourself, can a random engineer understand
the purpose of the function by its signature?
For Business Logic functions, the answer is often no, and a docstring (of input/output)
is often needed.

## Weird function signature

```python
def _parse_zip_examples(
    zip_bytes: bytes,
) -> list[tuple[list[str], dict[str, Any], bool]]:
```

This is litteraly something you gave me one time.
It is wrong on so many levels.
In this kind of situation either introduce more functions, or dataclasses,
or name tuple, ...
Nothing justifies this kind of signature. It is not self explanatory,
it is not clear,
it is not readable, it is not maintainable.

Also what kind of function returns a list instead of a tuple?
Even the "bytes", python have type aliases for a reason.

## Useless Tests

We use pytest for 2 things:

- Demo without polluting src
  - I have done that a lot on the beginning of the project,
  it was useful as a developper and purpose oriented.
  You rarely need to do that as an LLM.
- Unit tests (test that are automatically launched with `just test`)
  - You tend to create useless tests.
  - Always ask yourelf:
    - is my test too specific and creating maintenance burden?
    - is my test really algorithmic, or infra oriented?
      - typically outside of the libraries, tests often doesn't make sense
      - i'm not against 1-2 tests extremelly that can flag weird behavior
        but most of the time it doe not make sense. A unit test doe not have API
        keys. A unit test cannot launch a job. A unit test should only test a
        deterministic algorithmic behavior.

Currently each time I let CLAUDE generate a feature.
It will create a lot of tests that seems unnecessary instead
of creating good architecture and good code by design.
Don't flood the codebase with useless tests,
it is a maintenance burden. Each test should be justified.

Because you are not listening I have to specify something else:

- Stop hard coding values in those useless tests when it's not necessary.
  Often for scalar values you could have used boundaries constants and do
  things such as 15% of the boundary, boundary + 2, ...

Designing a good test that will not have to be updated on
each micro-changes in the future is hard,
that is why I don't like your badly designed tests.

## Cognitive Overload

Ultimately, the goal of the code is to be read by humans.
Those strict rules are my attempt
to give you a framework to write code that is readable and maintainable by **HUMANS**.

The most senior thing you can do is to reduce the amount of required comments,
explainations, bloat, and code.

I insist on this one, be **concise**, don't be verbose, be surgical.
