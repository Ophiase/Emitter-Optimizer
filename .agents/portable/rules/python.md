
# Python

The toolchain itself (uv, ruff/ty, `just precommit`) is described in
`AGENTS.md`. What follows is how the Python code in this repository is
expected to look.

## Code Practices

- We use type annotations everywhere, please make sure to add them to your code.
- Type aliases are the first tool for a readable signature. Whenever a
  primitive carries a meaning, name it: `MarkdownStr` says what `str` cannot,
  and `Annotated[int, Field(ge=0)]` carries its constraint with it.
  - Define each one once, in a module of types the code that needs it
    imports, never beside its first user. Two `Priority` types written in two
    places drift apart, and nobody notices which one a function takes.
  - A concept with a canonical order or bounds (a priority, a severity, a
    level) is a type, not a convention: an `IntEnum`, or an `Annotated` with
    its pydantic constraints. The order then lives in one place, and every
    comparison agrees on it.
  - An alias documents; it does not protect. When mixing two of them must be
    a type error, use `NewType` instead.
- Don't be lazy, never use single letter names, prefer descriptive names.
  - Also don't shorten names with abbreviations, for example `specification` is
  better than `spec`.
- Use the newest syntax the project's `requires-python` allows.
  - E.g. when possible in classmethods (not Enum), use `-> Self`
    instead of the class name in quotes.
  - prefer tuple[TypeA, ...] over list[TypeA]
    - They convey the immutability of the data.
    - perhaps tuple[TypeA, TypeB, TypeC] in
      function returns are often a poor way to concatenate multiple values,
      it make signatures really hard to read.
      It is not a contradiction, tuple for
      immutable sequences good, to concatenate values, often not good.
  - when possible functions should accept immutable types (e.g. Sequence instead
  of list) and return immutable types (e.g. tuple instead of list)
- Please professional code, i.e.
  - short functions
    - I insist on this one. A function should be short, we should not have to
      scroll to read the whole function and understand it.
      The signature of the function should be
      enough to understand what the function does.
      You can use type annotations and aliases to make the signature more clear
      if needed.
  - short files
    - Try when possible to avoid multiple classes
      in the same file. Don't hesitate to create a
      module if you have multiple related classes
      to implement
    - Be careful with the size of the files, if a file is too big,
      it's often a sign that it should be split into multiple files.
    - A lot of files in the codebase are too big,
      because they were generated by the LLM,
      so don't take as an excuse "oh, this other file
      is also too big, so it's ok if mine is too big". It's not ok.
      We want short encapsulated files.
  - single concern per function/file/class
    - the main thing I want you to adapt
      is the separation of concerns.
      You do not use OOP enough. Often
      I see you create file with 900 functions.
      Instead choose well defined abstractions to encapsulate algorithms.
      Force yourself to have clean contracts.
      Writing code is not supposed to be linear. But comming up with abstractions
      to solve sub problems in other files.
  - self explanatory code
    - A comment records a **why** the code cannot express. Anything else is
      deleted: a better name, a type alias or a small extracted function says
      it instead.
    - The rejected shapes — `HEADER`, `BANNER`, `STEP`, `NARRATIVE`,
      `VARIABLE`, `INLINE` — and the exempt tool directives are in
      [comments.md](comments.md), which covers every format.
      [comment-slop.sh](../checks/comment-slop.sh) reports them on the lines
      you just wrote.
    - What Python adds: a module docstring of three lines or more counts as a
      `HEADER`. A docstring is for a signature a reader cannot decode on its
      own — see [python-remarks.md](python-remarks.md) — not for a summary of
      the file.
    - Never explain in a comment what context a class is used in. Code is
      isolated bricks; let the reader focus.
- Classes reminder
  - pydantic BaseModel for anything public facing
    - e.g. API, and anything that is used for serialization/deserialization
    - Very useful with LLMs (validation + schema generation)
    - Please don't use comments to explain the fields,
      use concise pydantic Field descriptions instead.
  - dataclass for internal use
    - or pydantic.dataclasses.dataclass
      when validation is needed (e.g. sanitizer)
    - or when a dataclass is moved to schemas and needs to be public facing
  - StrEnum/IntEnum/Enum for enums
  - sqlalchemy for database models
    - remark: StrEnum should often be mapped onto
      str-based enums in the database, to avoid
      migration issues when changing the enum values
  - Try to do OOP when possible to ensure good
    encapsulation and separation of concerns.
    We use a lot of `@classmethod` and `@property` to
    ensure good encapsulation.
    If you need a factory for a tuple[TypeA, ...]
    you can also use a `@classmethod` to return it, instead of
    a standalone function.
- Typical sonarqube lints to have in mind:
  - Async functions should use async features (python:S7503)
  - Add a nested comment explaining why this method is empty.
- Please avoid Callable, use Protocol instead, it is more explicit and readable.
